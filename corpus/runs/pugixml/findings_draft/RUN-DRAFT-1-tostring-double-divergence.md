# RUN-DRAFT-1 — std::to_string(double) formatting diverges libc++ vs libstdc++

- **dedup_key**: tostring-double-formatting-libstdcxx
- **category**: fixture portability (run-local; not a binder or GCC bug)

## Symptom

pugixml gate, GCC 16 backend: `test_typed_attribute_conversions_differential`
failed 1/15 on BOTH lanes (constexpr + emit), surface=pass, compile/import green.
Reported as `D.value`. The failing assert was the price comparison
(`"%.6f" % price == E["b1_price_str"]`):

```
AssertionError: assert '9.990000' == '9.99'
```

## Root cause

A standard-library divergence, NOT a binding divergence:

- The native oracle serialized the parsed `as_double("9.99")` via
  `std::to_string(price)`.
- **libc++ (clang/macOS)** renders the classic 6-decimal `%f` form → `"9.990000"`.
- **libstdc++ in C++26 mode (GCC 16)** renders the shortest round-trippable form
  (`to_chars`-based) → `"9.99"`.

run_gates regenerates `expected.json` from the oracle each run, so the GCC oracle
wrote `b1_price_str = "9.99"`, while the test still formatted the Python-side double
with `%.6f` → `"9.990000"`. The test's `%.6f` assumption only held on libc++.

(Confirmed: `g++ -std=c++26 -O2` gives "9.99"; `g++ -std=c++17` gives "9.990000" —
the divergence is the C++26-mode libstdc++ `to_string`.)

## Fix (run-local only)

Make the price observation numeric instead of string-formatted, so it is
library-formatting-agnostic:

- `oracle_native.cpp`: emit `b1_price` as a JSON **number** (the `to_string` text
  "9.99" / "9.990000" both parse to the same JSON float).
- `test_bindings.py`: compare `price == pytest.approx(E["b1_price"])`.

Verified green on BOTH backends:
- GCC 16: `15 passed` constexpr + emit, surface=pass, outcome **E**.
- clang oracle (libc++) rebuilt natively: emits `b1_price` float 9.99; the binding's
  `as_double` returns 9.99 → `pytest.approx` matches. clang lane unaffected.

## Files touched (all under runs/pugixml/)

- `tests/oracle_native.cpp` — emit numeric `b1_price`, drop `b1_price_str`.
- `tests/test_bindings.py` — numeric `pytest.approx` compare.
- `tests/expected.json` — regenerated by the gate (now carries `b1_price`).

## Note for the wave

Any run that string-compares a `std::to_string(double)` / `std::to_string(float)`
observable will hit the same divergence on GCC. The portable pattern is to compare
the numeric value (emit it as a JSON number and use `pytest.approx`), or to format
both sides identically with `%.Nf`/`std::format` — never assume `std::to_string`'s
default precision.
